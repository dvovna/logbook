# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Logbook, a multi-tenant Slack app (NestJS 11, TypeScript) for vacation requests and time tracking: users request time off from the bot's App Home, the request goes through an approval workflow, and admins/HR manage users, teams, policies and holidays. Data lives in Supabase (Postgres).

## Commands

```bash
pnpm install
pnpm start:dev        # watch mode
pnpm start:debug      # watch + inspector
pnpm build            # nest build -> dist/
pnpm start:prod       # node dist/main
pnpm lint             # eslint with --fix, formatting included (see note below)
pnpm format           # prettier on src and test
npx tsc --noEmit      # type-check only
pnpm test             # jest
pnpm test src/request-workflows/services/request-workflow.service.spec.ts   # one file
pnpm test -t 'finishes the workflow'                                        # by test name
pnpm test:int         # integration tests against the local Supabase stack
pnpm test:cov:all     # unit + integration with merged coverage (coverage/index.html)
pnpm db:init          # recreate the local Supabase database from supabase/migrations
pnpm db:types         # regenerate src/common/types/database.types.ts from the local database
pnpm supabase start                                                    # local Supabase in Docker
pnpm slack:event src/commands/slack-events/team-join.json --team T0123ABCD   # signed event to the local app
```

- Integration tests are `test/integration/*.int-spec.ts` (config in `jest.integration.config.ts`, details in README → "Integration tests"):
  - They build the real `AppModule` through `configureApp` (`src/app.setup.ts`, shared with `main.ts`) and replace only `SlackApiClient` with `FakeSlackApiClient`, which records every Slack call.
  - `SlackTestClient` sends signed events, slash commands, interactions and external select suggestions (`suggest`). Every request fails when the app answers after 2.5 s (Slack gives up after 3). `submitView` builds `view.state.values` from the modal the app opened, so a form field that doesn't match its parser fails the test. Fields the test leaves out keep their initial value, as when the user doesn't touch them.
  - The fake refuses, like Slack, views and messages Slack would not accept (unknown fields, limits, an `initial_option` that is not among the options, duplicate `block_id`s; `support/block-kit-rules.ts`). When a look at the real Slack finds something like this, add a rule there.
  - File uploads go through the fake's `uploadFile`, recorded as `files.getUploadURLExternal` and `files.completeUploadExternal`; the rules refuse an empty file and a `channel_id` that is not a conversation ID (a `U…` user ID). `t.slackApi.uploadedFiles(token, channel)` returns the files shared in a channel with their content; a DM's channel is `D…` + the user ID without its `U`, as the fake answers `chat.postMessage`.

## Conventions enforced by lint/config

- Interfaces must be prefixed with `I` (`@typescript-eslint/naming-convention` reports an error otherwise).
- Every class member needs an explicit `public`/`private`/`protected` (`explicit-member-accessibility`).
- Single quotes, trailing commas and 2-space indent come from Prettier; `pnpm lint` or `pnpm format` applies them.
- Imports use the tsconfig path aliases `@modules/<module>/...` and `@common/...`. Absolute `src/...` paths also resolve (`src/*` in `paths`; TypeScript 6 deprecates `baseUrl`), but relative `../` imports are a lint error. Jest maps all of them in `moduleNameMapper`.
- Domain and shared code (the domain modules, `request-workflows` included, `src/common`, `slack-communication`) must not import the Slack UI in `src/slack` (`import/no-restricted-paths`). What both need goes into the domain module or `src/common`, e.g. `TimeEntryStatus` lives in `src/time-entries/enums`. A domain change that people should hear about publishes an event, and a listener in `src/slack` sends the messages. `src/common` in turn imports no feature module (a second zone of the same rule): the Slack request guards live in `src/slack/guards`, and `req.user` is typed in `src/slack/types/express.d.ts`.
- `src/common/types/database.types.ts` is the generated Supabase `Database` type. ESLint ignores it; `pnpm db:types` formats it with Prettier.

Not enforced by a tool: comments only for non-obvious things (why, constraints from Slack or Postgres, races and ordering); no comments that restate the code.

## Schema

The schema lives in `supabase/migrations`:
- `20260101000000_baseline_schema.sql` is the baseline. It holds every public table, constraint, index, comment and RLS flag of the dev project, taken with `pg_dump --schema-only` and made idempotent. On a database that already has the schema it is a no-op. On an empty one it creates the tables that the later migrations rely on.
- The later migrations add the read functions (`get_projects_list`, `get_user_projects`, `get_time_entries_list`) and constraints. The write functions they added once are dropped again (`20261110071250_drop_unused_write_functions.sql`): writes are TypeScript transactions.
- `src/common/types/database.types.ts` is generated from the local database by `pnpm db:types`, with the Supabase CLI pinned in `devDependencies` (another CLI version writes the file differently). CI applies `supabase/migrations` to a fresh stack, regenerates the file and fails when it differs from the committed one. Run the CLI as `pnpm supabase …` (or `npx supabase …`), never `supabase@latest`: scripts, CI and the integration tests all use the pinned one. Dependabot bumps it in a PR of its own; commit the regenerated file with it.

To change the schema:
1. Add a new migration (`pnpm supabase migration new <name>`). The app refuses to start on a database that lacks a migration it ships (`MigrationsCheckService`, which reads `supabase_migrations.schema_migrations`), and the Docker image copies `supabase/migrations` for that.
2. Apply it locally (`pnpm db:init`) and run `pnpm db:types`. A database with migrations from other branches gives other types.
3. Update the repository's `mapToViewModel`.

Pushing to the dev project:
- The dev project has every migration applied, the baseline included (it was a no-op there). New migrations go out with `supabase db push --remote` (the project is linked; without `--remote` CLI 3 pushes to the local database). Try `--dry-run` first. A migration older than the newest one on dev needs `--include-all`.
- The direct DB host is IPv6-only. From an IPv4 network, use the session pooler (`aws-1-us-east-1.pooler.supabase.com:5432`, user `postgres.<project-ref>`).
- Any other database that has the schema but not the migration history needs `--include-all` on its first push.

How the tables handle foreign keys:
- Every table has an FK to `slack_teams` with `ON DELETE CASCADE`. Uninstalling the app sets `slack_teams.uninstalled_at` and removes the token; `WorkspaceRetentionService` deletes the row after `UNINSTALLED_DATA_RETENTION_DAYS` and relies on this cascade, one workspace per transaction (`SlackTeamsService.deleteWorkspace`, with a 5-minute statement timeout), so one that fails doesn't keep the others. A reinstall before then restores the workspace (`TeamSetupWorkflowService`).
- Every foreign key has an index that starts with its columns (a partial one only when it leaves out nothing but nulls; `test/integration/schema.int-spec.ts` checks it). Postgres looks up the rows that point at a deleted row once per row and per key, and deleting a workspace cascades through all its users, projects and teams: without the index each lookup reads every workspace's rows. A new foreign key gets its index in the same migration.
- Every table has RLS enabled with no policies, and the `anon`/`authenticated` API roles have no table, sequence or function privileges, including by default for new objects (`20261107100000_lock_down_public_api.sql`). The app connects only as the owner of the tables (`DATABASE_URL`), which bypasses RLS; it doesn't use the REST API or its keys, and the API stays closed. A new table needs nothing extra. A new or re-created function does: PostgreSQL lets `PUBLIC` execute it, and default privileges set per schema can't take that back, so revoke it from `public, anon, authenticated` in the same migration (see `20261107130000_rejection_reasons.sql`); the app calls it as its owner and needs no grant. Never grant anything to `anon`.

## Architecture

### Multi-tenancy

Each Slack workspace that installs the app gets a `slack_teams` row. There are two different IDs to keep apart:
- `slack_teams.slack_id`: Slack's own `T…` workspace ID.
- `slack_team_id`: the internal UUID, used as the foreign key on every other table.

Every repository query must be scoped by `slackTeamId` / `slack_team_id`; `BaseRepository` throws when one isn't (see Domain layer). The bot token is stored on `slack_teams.slack_token`, encrypted with `SLACK_TOKEN_ENCRYPTION_KEY` (`TokenCipherService`, AES-256-GCM, `v1:` prefix); tokens stored in plain text before that are encrypted at startup and on first read. Every outgoing Slack call goes through `SlackCommunicationService`, which looks up the token per workspace via `AccessTokenService`; the token is cached for 1 day. With token rotation (on in the manifest) a bot token expires after 12 hours: `AccessTokenService` refreshes it 10 minutes before (`oauth.v2.access`, `grant_type=refresh_token`), once per workspace however many calls wait, and stores the new pair (`slack_refresh_token`, `slack_token_expires_at`, encrypted). The in-memory dedupe and cache are why the app runs as one instance. A token from before rotation has neither and never expires. Installing again updates the token (and clears the cache) and keeps the workspace's data and roles, which is how a workspace gets new scopes (`files:write` came after the first installs); a new install creates the workspace, its admin and the welcome and member-sync jobs in one transaction (`TeamSetupWorkflowService`). `SlackApiClient` keeps one `WebClient` per token. `views.open` gets one try with a 2.5 s timeout and fails at once on a rate limit, because its `trigger_id` lives 3 seconds; other calls get 3 quick retries and a 10 s timeout. `uploadFile` shares a file in Slack's three steps (`files.getUploadURLExternal`, the bytes to the upload URL on a Slack file host, `files.completeUploadExternal`; scope `files:write`). Its `channelId` is a conversation: for a DM, post to the user ID first and use the `D…` channel of the answer, since Slack refuses a user ID there and opening a DM would take `im:write` (`DmFileService` sends a file to the person who asked this way). `slackErrorOf(error)` reads the code of a failed call (`missing_scope`).

### HTTP pipeline for Slack (Slack Bolt's receiver is not used; Bolt is only imported for types)

`@slack/bolt` is a devDependency and is not in the production image. Import only types from it, with `import type` (`@typescript-eslint/no-restricted-imports` refuses any other import from it): a value import builds and passes the tests, then crashes the app in production.

1. `main.ts` mounts `slackBodyParserMiddleware` on `/api/slack`. It keeps `req.rawBody` for signature checks, then parses the body as JSON or urlencoded.
2. `SlackPayloadParseMiddleware` (wired in `SlackModule.configure`) unwraps the form field `payload` for `/interactions` and `/options`.
3. Guards (`src/slack/guards`, except the generic `UserRoleGuard` in `src/common/guards`) run in this order: `SlackSignatureGuard` → `SlackUserGuard` (loads the DB user by Slack user ID into `req.user`, with its workspace in one query: `UsersService.findInWorkspaceBySlackIds`) → `SlackActiveUserGuard` → `UserRoleGuard` + `@RequireRoles` (a route behind `UserRoleGuard` without `@RequireRoles` is closed to everyone). An unknown or deactivated user ends in `SlackUserAccessException`, which `SlackUserAccessFilter` answers with 200 and a short explanation the route allows (ephemeral reply, modal update, no options, or a DM for a click): Slack shows any other status as a generic failure.

Controllers are in `src/slack/controllers/`:
- OAuth: `/install` sets a random `state` in a cookie and redirects to Slack. `/oauth/redirect` checks the state against the cookie (OAuth CSRF), then calls `TeamSetupWorkflowService`, which creates the `slack_team`, an admin user and the jobs that send the admin a welcome DM with the setup steps and sync the workspace's users, all in one transaction. Until the workspace has a policy, company rules that name a level 2 approver (or every team keeping rules of its own), a team with approvers and everyone in a team, Home shows Admin and HR a checklist (`SetupProgressService`, which reads the rules through `TeamRulesService.forWorkspace`); its buttons open the company rules (a save re-renders Home) and send the team file, and the Home handler checks the role itself. The team form sets the team's members in one transaction (`set_team_members`).
- Users are looked up by workspace and Slack user ID together (`UsersService.findBySlackId(slackId, slackTeamId)`; unique `(slack_team_id, slack_id)`). On Enterprise Grid the same `U…` exists in several workspaces. The guards take the workspace from the request (`getRequestWorkspaceSlackId`).
- `/vacations` and `/log` slash commands (`/log` opens the Log Time form, as on Home).
- Admin commands.
- Events: home tab opened, `file_shared` (starts a file import), `team_join`/`user_change` (user upsert), `app_uninstalled`.
- Interactions.
- Options (external select search).

### Interaction dispatch (the most important pattern)

- Handlers are `@Injectable()` classes decorated with `@SlackHandler({ type, callbackId, allowedRoles })`. `allowedRoles` is required: a handler open to everyone says `ALL_ROLES` (role lists in `src/common/constants/role-groups.ts`).
- `SlackHandlersRegistry` finds them at startup through `DiscoveryService` and keys them by `${type}:${callbackId}`. The app refuses to start on two handlers for one key, a handler with no roles, or a `ViewCallbackId` without a handler (read-only modals are listed in `READ_ONLY_VIEWS`).
- How `callbackId` is resolved:
  - `view_submission`: `view.callback_id`.
  - `block_actions` in an App Home tab or a modal: the view's `callback_id`.
  - `block_actions` in a message: the **`block_id` of the first action**, so actionable blocks in messages use the matching `ViewCallbackId` as their `block_id`.
- Slack takes `action_id`, button values, menu choices and form values from the client: a member can send ones the UI never offered. `callback_id` and `private_metadata` come from the stored view. So every handler and service checks the role and that an ID from the client is the workspace's and the user may use it; hiding a button is not access control (`test/integration/access-control.int-spec.ts`, `object-access.int-spec.ts`).
- `SlackInteractionsService` enforces `allowedRoles` and blocks inactive users before it calls the handler.
- `BaseActionHandler` (for `block_actions`) dispatches on `action_id` through `actionMap`. `BaseTabActionHandler`, which every tab's handler extends, opens the screen any navigation button names (`NavigationActionId`). Helpers such as `withPagination`, `withMenuAction` and `withButtonAction` unpack action values.
- `BaseModalFormSubmitHandler<Metadata, FormData, Result>` (for `view_submission`):
  - Parses `private_metadata` as JSON.
  - Validates the view with its parser, an `IFormParser` (`parse(view)`, `blockIdOf(field, view)`; `src/slack/common/types/form-parser.types.ts`), returning field-level errors. Most forms use a `BaseValuesParser` (a zod schema plus field config, read from `view.state.values`); the week and day forms have `TimesheetFormParser`, whose cells are dynamic.
  - Calls `onSubmit`.
  - Shows the message of a refusal (`ValidationError`, `DuplicatedRecordError`, `MaxItemsCountReachedError`, `EntityHasDependenciesError`, `PrimaryEntityDeleteError`) or a `ForbiddenException` in the modal; any other error, a missing record included (some of those messages name internal IDs), shows a generic message. `classifyActionError` (`src/slack/common/utils/action-errors.ts`: refusal, not-found, forbidden, unexpected) sorts them for forms and for the buttons that decide the same (Approvals, My time, the time off offer), each showing them its own way.
  - A `ValidationError` or `DuplicatedRecordError` that names a field (in domain terms: `dates`, `minutes`, `project`, `name`) is answered with `response_action: errors` at that field's block, so Slack keeps the input. A form whose field has another name maps it in `errorFields` (e.g. `{ minutes: 'hours' }`), and the parser's `blockIdOf` finds the block (a versioned one too).
  - Build responses with `SlackViewResponseFactory`. A form opened from a tab closes on success (`success()`, `response_action: 'clear'`) and re-renders its tab with a one-line `notice` ("✅ Client Acme created."), which `BaseTabService` puts under the navigation row (`block_id` `tab_notice`, read in tests with `noticeOf`). A form opened by a slash command (`/log`, `/vacations request`, `/vacations cancel`) has no tab and re-renders Home the same way. There are no Success screens.
  - A parser reads each field by its config key as the `action_id`, so the view element must use that key as its `action_id`. The integration tests' `submitView` fills forms from the real view and catches a mismatch.
  - A form that changes what its fields show (the report forms' quick period fills From and To; the week form's Add a project, Show weekend and day, which answer at once and rebuild it after the answer with `runInBackground`, passing the click's `view.hash` so that an older click's rebuild fails with `hash_conflict`, logged as a warning, instead of replacing a newer one) is rebuilt with `views.update` (`SlackCommunicationService.updateView`, by the interaction's `view.id`; the fake records it, `t.slackApi.updatedModal`). Slack keeps what a field with the same `block_id` holds, so the changed fields get a versioned `block_id` (`versionedBlockId`, `from_date_block:<version>`), which the parser finds by its configured one; the other fields keep theirs and what the user chose.
- Slack shows an interaction as failed when the answer takes over 3 seconds. Work that updates several messages or notifies people (deciding workflow steps, "Approve for Approvers") runs after the answer through `runInBackground` (`src/common/utils/run-in-background.ts`), which logs its errors. Checks that can fail run before it, so the modal can still show them. `EventTrackingService` routes `EventEmitter2.emit` through `emitAsync`, so `@OnEvent` and tab navigation listeners count as such work as well. On SIGTERM the app waits up to 8 s for all of it before it closes (`BackgroundWorkShutdownService`; `docker stop` kills after 10). A failing listener is logged and not retried; work that must not be lost is a job (see Background jobs).

To add an interaction:
1. Add a `ViewCallbackId` value (`src/slack/enums/integration-callback-id.enum.ts`).
2. Create the decorated handler with its `allowedRoles`.
3. Register it as a provider in its feature module (otherwise the app does not start).

### App Home "tabs"

The UI is a single App Home view that gets re-published to show different screens. Navigation is by task, in one row: `[Home] [My time] [Time off] [Approvals (N)] [☰ More ▾]`. The More menu (a `static_select`, `nav_menu`, whose option values are the screens' `NavigationActionId`s) holds People and Reports under "Manage" and Teams, Policies, Projects, Clients under "Settings", and shows the screen open from it. Members see Home, My time, Time off and Reports: a menu of one screen is a button. Approvals is one inbox of time off and time entries waiting for the viewer. `nav_settings` is no longer shown but still opens the first Settings screen, for views published before the menu.

- Every screen is in the registry `SCREENS` (`src/slack/common/navigation/screens.ts`): title, roles, the tab that shows it, the action that opens it, and its parent (Back) or More menu group (`menuGroup`). `ScreenHeader` builds the navigation row, its menu and Back from it, and `BaseTabService` puts the header (with the Approvals count, `PendingApprovalsService`, counted beside the screen's own reads and handed to Home as a promise) above every screen. A tab's action handler allows `rolesOfTab(TabId.X)`. A new screen needs an entry there; `access-control.int-spec.ts` follows every button and menu option for every role. In tests, `openAppHomeTab(t, workspace, user, [NavigationActionId.Teams])` opens a screen by its button or its menu option (`navigate` in `support/app-home.ts`).
- Each tab lives in `src/slack/tabs/<name>/`, with `handlers/`, `parsers/`, `services/` and `views/` and its own Nest module. A tab can show more than one screen: `TimeEntries` is My time (`ownEntriesOnly`) and Time logs; `screenOfTab` picks by metadata.
- A tab service extends `BaseTabService`. In `onModuleInit` it subscribes to `TabNavigationService` (EventEmitter2 events named by `TabId`).
- `tabNavigationService.navigate(TabId.X, { user, metadata })` re-renders a tab from anywhere.
- Tab state such as pagination and filters round-trips through the view's `private_metadata`. Modals carry it along as `pageMetadata` so they can re-render the tab after a submit.
- If rendering fails, the user sees `FallbackTabView`; inactive users see `InactiveUserTabView`.
- `BaseTabService.publish` checks the screen's roles and sends anyone else to Home. Hiding a button is not access control: Slack takes action ids, button values and menu choices from the client. So every handler checks the role (`allowedRoles`) and every service checks the owner. Actions inside a screen that only some of its roles may use are in `SlackActionPermissionsService`.
- Views are injectable classes that return Block Kit JSON.
- A list item is `ListItem` (`src/slack/common/views/components/list-item.view.ts`): a bold title, short detail lines with empty ones left out, a menu (one with a single option shows as a button with the menu's `action_id`; `withMenuAction` reads both), buttons. Time entries are grouped by day, each day with its total. The names and icons of statuses and types (vacation type and status, workflow step, time entry, project) come from one dictionary, `src/slack/common/views/data/labels.ts` (`withIcon` gives '⏳ Pending', `labelOptions` the options of a select or filter, `personLabel` the name or else the email); a view writes none of them itself. Read-only data goes into a `table` block, which App Home and messages have and modals don't: time, billing and uninvoiced reports show on Reports, one at a time (`fitTableRows` in `src/slack/tabs/reports/views/report-table.ts` keeps a table to 100 rows and 10000 characters), and the test fake refuses a table in a modal or a second one in a view.

### Domain layer

Domain modules: `users`, `teams`, `vacation-policies`, `vacation-requests`, `holidays`, `slack-teams`, `request-workflows`, `team-file`. They follow Repository → Service:

- **Repositories** extend `BaseRepository<'x', ViewModel>` (`src/common/repositories/base.repository.ts`). It queries Postgres directly over `DATABASE_URL` (`DatabaseService`) with Kysely 0.28, typed from `database.types.ts` (`src/common/types/sql-database.types.ts`), and does no ORM work. Kysely 0.29 is ESM-only, so the project stays on 0.28. Subclasses set:
  - `tableName`;
  - `relations` (many-to-one, `{ table, foreignKey, columns }`, embedded in each row as an object or null);
  - `searchableColumns`;
  - `mapToViewModel`.

  Filters are `RepositoryFilter` (`repository.types.ts`). A filter value can be a plain value (`eq`; `null` means `is null`), a list (`in`) or `{ operator, value }`. A filter value that is `undefined` is left out, so the repository refuses any query or insert on a workspace's table without `slack_team_id` (and any query on `slack_teams` without a filter); `workspaceColumn = null` turns this off for `slack_teams` only. A repository's own queries start from `selectInWorkspace`/`updateInWorkspace`/`deleteInWorkspace`, which add the workspace condition. `%` and `_` in a search term are text.

  `findOne` returns null only when no row matches, and throws on a failed query or several rows. `update` changes exactly one row or throws and changes nothing. An empty list in a filter matches no row. A key left `undefined` in an insert, update or upsert is left out, so an upsert keeps that column. Rows come back in the formats PostgREST used, which the view models were written for (`src/database/pg-type-parsers.ts`: timestamps as ISO strings with microseconds, dates as text, bigint and numeric as numbers). Writes that change several rows or tables are TypeScript transactions in the services (e.g. replacing imported vacations or holidays, a project's assignments, a team's members). The read functions (`get_projects_list`, `get_user_projects`, `get_time_entries_list`) are called over the same connection with `callFunction` (`src/database/sql-functions.ts`), by the names `pnpm db:types` generated; a jsonb argument goes in as `JSON.stringify(...)`.
- **Transactions:** services use `TransactionService`, never `DatabaseService` (a lint zone). `transaction(work)` runs every repository call inside `work` in one transaction (AsyncLocalStorage); `afterCommit` runs work after the commit, `lock(lock)` takes an advisory lock till its end. Every lock key is in `src/database/advisory-locks.ts` with a rank: a request's `vacationRequestLock`, then its `workflowLock`, then a person's `timesheetLock`; locks of one rank go in the order of their keys (`compareLocks`, so an import closing several requests sorts their IDs). A transaction that takes a lock coming before one it holds throws before any SQL (it could deadlock), and `lockInOrder(...locks)` takes several in order. A write that needs a lock its caller takes checks it with `assertHolds(lock)`. An event emitted inside reaches its listeners after the commit (`EventTrackingService`). No Slack calls inside a transaction. The pool's connections have a 10 s statement timeout, set with the time zone in one statement when a connection opens (`SESSION_SETUP`); `allowLongStatements(seconds)` lifts it for the rest of one transaction, for background work that is big by nature (deleting a workspace). An idle connection stays open a minute (`IDLE_CONNECTION_MS`, TCP keepalive after 30 s), since opening one costs several round trips. Inside a transaction every statement waits for the one before (one connection): read what doesn't need the lock on the pool instead, at once (`Promise.all`) and before or beside the transaction, as `TimesheetSaveService.saveCells` reads the projects and `VacationRequestsService.checkUpdate` what it checks.
- **Services** take camelCase params and convert them to snake_case filters, usually in a private `getFindQuery`. Services also enforce per-workspace limits from env (`MAX_TEAMS_PER_SLACK_TEAM`, `MAX_POLICIES_PER_SLACK_TEAM`, `MAX_*_REQUESTS_PER_USER`) and throw the domain errors from `src/common/errors/`.
- Only an admin grants or removes the Admin or Finance role, or deactivates an admin (`assertCanChangeUser`). Nobody approves their own vacation request: requesters are left out of their own approval levels, and `RequestWorkflowService.assertNotOwnRequest` guards the approve paths. A Slack `user_change` can deactivate a user but never reactivates one.
- `slack_teams.slack_token` stays out of `ISlackTeamViewModel`; only `AccessTokenService` reads it, through `SlackTeamsService.findAccessToken`.
- Company rules (`rule_sets`, one default set per workspace, `CompanyRulesService`): the level 2 approvers and their rule, who hears of decisions, and the vacation policy. A team follows them while `teams.rule_set_id` is set, and keeps its own rules (the columns on `teams`) while it is null; a team that follows them may still hold old values in those columns, which nothing reads. Everyone in no team follows them. Level 1 always comes from the team. Every reader of these rules asks `TeamRulesService.forTeam(teamId, slackTeamId)` (`forWorkspace` for the company rules and every team's rules in one read), which gives the company rules, with no level 1, for no team or a team that isn't the workspace's; only level 1's readers (`TimeEntryApprovalsService`, the manager scopes) read `manager_approvers` directly. A policy the company rules use can't be deleted.
- Admin and HR see everyone's people and vacations (`isPeopleAdmin`); a manager only the teams that list them in `manager_approvers` (`TeamsService.findManagedTeamIds`, `scopeTeamFilter`, `assertManagesTeam`), whatever team a filter names. The people searches of external selects follow the viewer's role, not the select the client names (`UserOptionsService.searchUsers`): Admin and HR find everyone, a manager the people of those teams, a member nobody; only a project's assignments offer a manager everyone, since projects are the workspace's and the form offers every team. Only the approver of a workflow step, or HR/admin, decides or comments on it (`RequestWorkflowService.assertCanActOnStep`). Members log time only on `get_user_projects` projects. IDs taken from forms (teams, clients, policies, project assignments) are checked to be the workspace's.
- Text people typed (comments, reasons, descriptions, people's names) goes into mrkdwn through `escapeMrkdwn` (`src/slack/common/utils/mrkdwn.utils.ts`), so it can't become a link or a mention.
- Roles (`UserRole`), one per person; the role lists are in `src/common/constants/role-groups.ts`:
  - `admin`: full access;
  - `hr`: manages people and requests, and sees everyone's time without rates or amounts;
  - `manager`: approves;
  - `finance`: rates and the projects that carry them, amounts, billing reports, snapshots and the uninvoiced report (`BILLING_ROLES`, with Admin), and everyone's time in reports; logs and requests like a member, approves nothing, manages no people, teams or policies;
  - `member`.

### Vacation request approval flow (event-driven, EventEmitter2)

1. `VacationRequestsService` emits `vacation_request.created`.
2. `VacationRequestProcessingService` builds the workflow levels from the rules of the request's team (`TeamRulesService.forTeam`):
   - level 1: the team's `manager_approvers`;
   - level 2: the team's `hr_approvers`, or the company rules' when the team follows them. A person in no team has no level 1 and gets the company rules' level 2.

   Each level has an `ApprovalRule` of `ANY` or `ALL`. A level takes only the people its rules name who can decide a step (`canApprove`: active, with Admin, HR or Manager; the approver DM's buttons allow those roles). If nobody those rules name can approve it (no team and no company level 2, no approvers, nobody who can decide, or the requester is the only one), it goes as one `ANY` level to everyone with the HR role, else to every admin, never to the requester. The levels are stored when the workflow starts, so a change to a team's rules or the company rules applies to requests made from then on. With nobody else in the workspace, no workflow is created. Either way the requester gets a DM saying who the request went to, or that nobody can approve it yet and it stays pending, with the teammates who are off on those days (approved or pending, sick leave left out; `TimeOffContextService`). After each level that isn't the last they get another DM: who approved and who decides next (`VacationRequestProgressNoticesService`).
3. `RequestWorkflowService` stores one row per approver in `request_workflow_steps` and activates level 1 through `WorkflowStepProcessorService`. The steps of one workflow share a run (`step_data.run`, `src/request-workflows/utils/workflow-runs.ts`; the request's ID for the first run): an edit by HR or an admin that changes the dates, type or person of a pending request closes the open steps and starts a new run with the request as it is now (`handleRequestUpdated`), and the progress lines, the requester's notices and the details show only the current run (`currentRunOf`). An edit of only the comment leaves the workflow alone.
   - When someone is deactivated (People, or a deleted Slack account) or loses an approving role, `UsersService` publishes `USER_ACCESS_CHANGED`, and `ApproverAccessService` (a job) closes their open steps through `RequestWorkflowService.dropApprover`. A level left with nobody moves on as a new request would: done when someone on it approved (`ALL`), else the next level with anyone on it is asked (`activateNextLevel` passes over emptied levels), else HR or the admins get the level.
4. Step processors are registered with `@WorkflowStepProcessor(type)` and found by `WorkflowStepProcessorsRegistry` (the same discovery pattern as Slack handlers). The only type is `approver`: `ApproverStepProcessor` sends each approver a DM with Approve / Reject / Comment buttons. `WorkflowStepProcessorService` asks and updates in jobs, one per step; a decided or canceled step is marked `completed_at` first, so a Slack failure never stops the workflow. The approver's DM, its buttons and forms, and `ApproverStepProcessor` are the Slack side, in `src/slack/approvals` (`ApprovalsModule`); `request-workflows` holds the workflow itself.
5. Button clicks go to `ApproverStepMessageHandler` (`block_id` `workflow_step_message`):
   - The DM carries a context line: the requester's balance after the request and teammates off on those days (put into the workflow snapshot when it starts), the level and who approved earlier levels. Levels have names ("Manager approval", "HR approval", "Admin approval") in `step_data.level_name`, which the Details timeline shows.
   - `ANY`: one approval completes the level.
   - `ALL`: the level waits until there are no pending steps.
   - Someone who approved an earlier level of the run isn't asked again: when a level opens, their step is approved as them (`activateNextLevel`), which completes an `ANY` level, or an `ALL` one with nobody else on it.
   - A reject at any level ends the workflow.
   - Comments re-render the messages of all pending steps, and the requester gets each one at once in a DM with View Details and Cancel buttons (`VacationRequestProgressNoticesService`, buttons in `RequesterNoticeMessageHandler`).
   - By design a step is not tied to the user who clicks: HR and admins may decide for an approver who is away, so a request doesn't get stuck. In the UI they do it with "Approve for Approvers" in All requests (Approvals → All pending requests) (`ApproveVacationRequestOnBehalfHandler` → `RequestWorkflowService.approveCurrentLevel`), which approves every open step of the current level and moves on.
6. When the workflow finishes it emits `VacationWorkflowFinished`. `RequestWorkflowProcessingService` then sets the request status (a job) and publishes `vacation_request.decided`. On the Slack side, `VacationDecisionNotificationsService` (Vacation Requests tab module) notifies the requester and each notification recipient of the request's team rules (the company rules' for a team that follows them or a request in no team), read when the request is decided, one job per message.

Two approvers can click at the same moment, so the transitions are single conditional updates rather than "read, check, write". A decision (approve, reject, cancel, delete, "Approve for Approvers") is one transaction (`RequestWorkflowService`): an advisory lock per request, then one `UPDATE` (`RequestWorkflowStepsRepository.decide`) that writes the status into `step_data` and sets `completed_at`, only on steps that are still open, and returns the steps it decided (none when someone else was first, and then the caller stops). The jobs that follow it (asking the next level, refreshing the messages, finishing the request through the `Finished` event, delivered with `emitAsync` inside the transaction) are enqueued in the same transaction, so a decision never stays without them. The lock matters for the ALL rule: two approvers deciding at once would otherwise each miss the other's uncommitted decision, and nobody would ask the next level. `VacationRequestsService.finishPending` changes only a request that is still pending (whoever changes it sends the notifications), and the next level's steps are claimed through `processed_at` (`claimUnprocessed`) before anyone is asked.


### Time & Billing

Domain modules `clients`, `projects`, `time-entries`, `billing` (snapshots, the uninvoiced report); Slack tabs `clients`, `projects`, `time-tracking` (Log Time modal, My time and Time logs), `approvals` (the Approvals inbox, with time off), `reports` (the week, time reports and their CSV, billing report and locking it in a snapshot, uninvoiced report), `billing-snapshots` (Reports → Billing snapshots).
- Projects belong to an optional client and are assigned to teams and users (`ProjectAssignmentsService`, one transaction). People log time on their team's and their own projects (`get_user_projects`). `TIME_ENTRIES_ADMIN_ROLES` (Admin, HR) log for anyone on any active project and see and edit everyone's entries; everyone else sees only their own, and Home → Edit Entries shows only your own for every role.
- An entry takes its client and billability from its project. Minutes come in 15-minute steps, at most 24 hours per user, project and day (also a check constraint).
- Status: the owner logs drafts and submits them; a submitted entry is approved or rejected in the Approvals tab by the managers of its team (`manager_approvers`, as for vacations), HR or an admin, never by its owner. What waits for whom is one rule in SQL (`TimeEntriesRepository.approves`): the entry's team's active approving managers other than the owner; when there are none (no team, no manager, only the owner), HR, or the admins when nobody else has the HR role, as time off does. Admin and HR may still decide anyone's (Approvals → All pending entries), but their inbox, its count, Approve all and the DMs on submission hold only what waits for them; the count is `count(*)` over the entries grouped by team and owner, so the rule runs once a pair. Submitting publishes `time_entries.submitted`, and each approver gets one DM of what waits (`TimeEntryNotificationsService`, a job). A rejection sends the owner a DM. Once a week, from Monday 09:00 UTC, people with drafts or rejected entries from before that week get a reminder (`TimeEntryRemindersService`, checked every 10 minutes; `slack_teams.time_reminder_week` keeps a restart from sending it twice). A workspace's reminders are saved in one statement (`jobs.enqueueMany`) in the transaction that claims the week, and go out 5 a second; a workspace that fails is logged and reported, keeps its week unclaimed for the next tick, and doesn't stop the others. The owner changes only drafts and rejected entries (a fixed one is a draft again).
- Lists come from `get_time_entries_list`.
- The week on My time (`TimesheetWeekService.getWeek`): a `table` block of every project with the viewer's time that week (no row cap; `fitTableRows` guards Slack's limits), Monday to Friday plus Saturday and Sunday only when they hold time, with day totals and a status line. The tab's metadata holds `weekStart`, which previous/next week change; it replaces My time's From/To, and the project filter stays and narrows only the list. "Submit week" is `TimeEntriesService.submit` narrowed to the week's dates. A line under the table counts the viewer's drafts and rejected entries dated before the shown week (`TimesheetWeekService.findOpenBefore`), with a button to the oldest week holding one; the rejection DM names the week of the entry, and the Monday reminder the dates of the open entries and the weeks of the rejected ones. Time logs has no table and keeps From/To.
- The week and day forms are one modal (`TimesheetFormMetadata.mode`, `'week' | 'day'`):
  - Rows are the projects with the viewer's time in the shown week or the 4 before, plus the ones added with "Add a project" (`TimesheetWeekService.allowedProjects`: `get_user_projects`, every active project for Admin and HR). At most 10 rows (`MAX_TIMESHEET_ROWS`), ranked before the cut: time in the shown week, then added, then older ones the viewer may still log on (an archived or no longer theirs project with no time in the shown week gets no row).
  - A cell with no entry, or exactly one own draft or rejected entry that isn't billed, is an input; any other is read-only text with the reason (`TimesheetCellLock`: several entries, submitted, approved, billed, project not the viewer's or archived). The domain knows a cell as a project and a day (`ITimesheetCellChange`, `TimesheetCellError` for what is refused at one, with its `TimesheetCellLock`); the form's keys and words are Slack's: `cellKey(projectId, date)` (`src/slack/tabs/time-tracking/utils/`) is the `block_id` and `action_id` of an input, and the lock's words are in `labels.ts`. Empty or `0` is no time; anything else goes through the Log Time hours schema.
  - A cell whose value is still what the form showed (`initial_value`, read from the submitted `view.blocks`) is skipped. A touched cell whose current minutes differ from what the form showed (`expectedMinutes`) is refused at that cell: a form opened before a change doesn't undo it. A rebuild of the form (Add a project, Show weekend, the day, an error) keeps what it first showed in the cells it already had (`TimesheetFormParser.shownMinutes`), so a change made elsewhere meanwhile isn't overwritten either; such a cell says what it holds now (its input's hint).
  - `TimesheetSaveService.saveCells` reads the projects on the pool while its transaction starts and takes the lock, then under `timesheetLock` the week's entries with whether they are billed in one query (`TimeEntriesService.findOfUserWithBilled`), checks all cells in memory with `TimeEntriesValidationService`'s read-free checks (`checkCreate`, `checkUpdate`, `checkDelete`, `checkDailyTotal`; the 24 hours count the cell's cancelled entries too), and writes one statement per kind (`insertMany`, `writeMinutes`, `writeDeletes`) in one transaction; the first failure in the form's order is an error at its cell, an entry that changed since its check included. The minutes in its notice come from that read and the changes. A rejected entry that is changed becomes a draft again. The day form has a comment, which goes on created and changed entries and replaces a description only when filled; a comment with no changed cell is refused at the comment field. A checkbox on the week form ("Submit the week's time for approval") submits the week's entries in the same transaction. My time then shows the form's week (for the day form, the saved day's) with a one-line notice of what the week or the day holds.
- Writes of time entry rows are `TimeEntryWriter`'s (`src/time-entries/services/time-entry-writer.service.ts`): a new row through `insert` (Log Time) or `insertMany` (the timesheet, and time off logged as time with its `vacationRequestId`); a change or deletion made in a form through `writeUpdate` and `writeDelete` (Log Time's edit and delete), or `writeMinutes` and `writeDeletes` for many at once (the timesheet), which write only while the entry is as it was checked (not deleted; still a draft or rejected where only such an entry may change), else `TimeEntryChangedError` (the batch ones return the IDs they left alone); a vacation's linked time through `deleteLinkedToVacation` (one statement). `TimeEntriesService` is Log Time's create, edit and delete with their checks (`TimeEntriesValidationService`: each `validate*` reads what its rule needs and calls the read-free `check*` the timesheet uses), the finds and `submit`; status changes (`submit`, the decisions of `TimeEntryApprovalsService`) update rows directly.
- Time off as time (`src/time-off-logging`: `TimeOffSettingsService`, `TimeOffLoggingService`):
  - An admin sets, on Projects, a project per leave type (annual leave, bonus days, sick leave, unpaid leave; not Other) and the hours of a working day; Projects shows what is set under the button (`TimeOffSettingsService.getSetup`; a type whose project is archived shows as unset). They are stored in `slack_teams.time_off_minutes_per_day` (default 8 hours, 15-minute steps) and the table `time_off_projects` (`slack_team_id`, `vacation_type`, `project_id`). Projects are archived, never deleted, so a mapping ends by archiving, and an archived mapped project means no offer; only a workspace deletion cascades.
  - The offer is a button "Log <hours> to <project>" in the requester's DM about an approved request, or a DM of its own when HR or an admin creates a request as approved or edits one into approved (`VacationRequestUpdatedEvent.previous`; the workflow's own approval carries none, so it gets the button only in the decision DM). The decision DM never depends on the offer: when working it out fails, the DM goes without the button. A deactivated requester gets no offer. A CSV import offers nothing.
  - The click (`TimeOffLoggingService.log`; the requester only, the request approved only) logs one approved entry per working day (`VacationDaysCalculationService.workingDates`), linked by `time_entries.vacation_request_id`, described by its leave type (`TIME_OFF_DESCRIPTIONS`, the domain's words: domain code doesn't import `labels.ts`). It runs under `vacationRequestLock`, then the timesheet's `timesheetLock` (`lockInOrder`), writes through `VacationTimeService.log`, and skips days with the requester's time on the project, or with time linked to this request on any project, so a second click writes nothing. The result message is built from the request's linked entries, so every click tells the truth; a failure after the answer is told in an ephemeral message.
  - When HR or an admin changes a request's dates, status, type or person (`changesLoggedTime`), or deletes it, its non-billed linked entries are soft-deleted in the same transaction and under the same lock. `TimeOffChangesService` runs both (`VacationRequestsService.checkUpdate`/`applyUpdate`/`applyDelete`, then `VacationTimeService.remove`), so the vacation module knows no time entries. It takes the request's lock, which `applyUpdate` and `applyDelete` check, and a lint rule (`no-restricted-properties`) keeps those two to `src/vacation-requests` and `src/time-off-logging`. A member's cancel needs no cleanup, since a pending request holds no logged time; it checks the request is still pending under the lock. Billed ones stay, and the changer's notice names those days. A request that is still approved gets a new offer. When time went (`TimeOffChangedEvent.removedTime`, by the person who logged it), that person gets a DM saying what happened (changed, rejected, canceled, waiting for approval again, deleted, moved to someone else), the hours that went and the billed days that stay: in the new offer's DM when the request is still theirs and offers again, else on its own, and a new person gets the offer in a DM of their own (the offer job, `removed` in its payload, which carries the facts: the request may be gone). A CSV import keeps the hours and drops the link (`ON DELETE SET NULL`).
- Rates: a project has an `hourly_rate`, and a person may have their own rate on a project (`project_user_rates`, `ProjectRatesService`), which replaces it. That table is apart from `project_users` because the assignments form replaces those rows (and managers use it), people on an assigned team have no row there, and a rate has to outlive an assignment for past time. Rates and amounts are Admin's and Finance's (`RATE_ROLES` = `BILLING_ROLES`, `assertCanSeeRates` in `src/projects/constants/rate-roles.ts`); HR sees neither: `ProjectsService` and `ProjectRatesService` refuse anyone else, the project form and Person Rates modals refuse to open for them, and Projects shows rates and the currency to them only. Amounts are whole cents (`src/common/utils/money.utils.ts`).
- Currency: one per workspace, `slack_teams.currency` (ISO 4217, default USD). An admin changes it on Projects (`SlackTeamsService.setCurrency`); the rates keep their numbers.
- Billing reports (Admin and Finance, checked in `BillingReportService` too) count approved entries of a client's projects for a period: a table of each person's time on each project with its rate and amount, a total row, and the totals by project and by person. Billable time with no rate has no amount and is counted apart. Reports use today's rates; a billing snapshot freezes them. The billing report also says how much of its approved time snapshots hold, and offers to lock the rest.
- Whose time a report shows comes from the viewer alone (`TimeEntriesScopeService`), never from the form or the view's metadata: Admin, HR and Finance everyone's (`COMPANY_TIME_ROLES`); a manager the entries logged in the teams that list them in `manager_approvers` (by `time_entries.team_id`, as in Approvals) and their own; everyone else, and a manager of no team, their own. The week on Reports uses the same scope.
- Report forms have a quick period (this or last week, month, quarter; All time on the uninvoiced one) that fills their dates (`ReportFormPresetHandler`, `src/common/utils/period-presets.ts`, weeks from Monday, a "this" period up to today).
- Time reports (`TimeReportService`, every role, so Reports is open to members) count every entry of a period but deleted ones, by client (the project's client, as billing does), project, person or team: hours, billable, approved, and for `RATE_ROLES` amounts of all billable time at today's rates. "Who hasn't submitted" lists the active people of the viewer's scope who logged nothing in the period or still have drafts or rejected entries in it; the form offers it to `OTHERS_TIME_ROLES` (managers, HR, Admin and Finance). A period is a year at most (`assertReportPeriod`). Its form also narrows the report, and its CSV, to a client, a project or a person (`TimeReportService.findFilteredEntries`, after the scope, so no ID can widen it; an ID the viewer may not see matches nothing). Members filter by project only (their own projects); the person filter offers the people of the viewer's scope (`UserOptionsService.searchPeopleInScope`); "Who hasn't submitted" doesn't use the filters.
- The CSV export (`TimeEntriesExportService`, sent by `TimeReportExportService` through `DmFileService` after the answer, with `runInBackground`: a file hours later is no use) has one line per entry of the time report on show: Date, Person, Email, Team, Client, Project, Description, Hours, Billable, Status, and for `RATE_ROLES` Rate, Amount (the entry's billable time at the person's or the project's rate, rounded to the cent) and Currency. `src/common/utils/csv.utils.ts` writes it for spreadsheets: a UTF-8 byte order mark, CRLF, and a `'` before typed text that starts like a formula. A workspace without `files:write` gets a DM asking to install the app again.
- Billing snapshots (`src/billing`, `BillingSnapshotsService`; tables `billing_snapshots` and `billing_snapshot_entries`) lock a client's approved time of a period for an invoice made elsewhere; Logbook makes no invoices. Admin and Finance (`SNAPSHOT_ROLES`) lock the billing report on show from Reports ("Lock in a snapshot", which confirms what it takes) and mark a snapshot invoiced, or not invoiced again, on Reports → Billing snapshots, which filters by client; only an admin unlocks one, which deletes it and frees its entries, an invoiced one too (the form warns that the invoice was sent).
  - A snapshot takes the approved entries of the client's projects (archived ones too) in the period that are in no snapshot: `billing_snapshot_entries.time_entry_id` is the primary key, so an entry is in one snapshot at most, and a second snapshot of the same period takes only time approved since.
  - Each line keeps the entry's rate (the person's own on the project, else the project's) and amount, rounded per entry so the lines add up to the totals; the snapshot keeps the totals and the currency.
  - One transaction: an advisory lock per workspace, then the entries are read `FOR UPDATE`, so none changes before the snapshot commits.
- An entry in a snapshot is locked for everyone, Admin included. `TimeEntriesValidationService` refuses its edit, deletion or status change, and Time logs shows it as billed without Edit and Delete. The trigger `time_entries_keep_billed` refuses any other write of its content (SQLSTATE `LB001`, which `TimeEntriesService` turns into the same message); a hard delete fails on the foreign key. Deleting a team leaves its entries without a team (`ON DELETE SET NULL`).
- A snapshot's CSV (`BillingSnapshotExportService`, sent like the time report's through `DmFileService`) has one line per entry: Date, Person, Email, Team, Project, Description, Hours, Billable, Rate, Amount, Currency, with the frozen rate and amount. One client and only approved time, so no Client or Status column.
- The uninvoiced report (`UninvoicedReportService`, Admin and Finance, on Reports, for a period from its form: all time by default, and a date left empty is no limit on that side) shows per client the approved billable time in no snapshot, with its amount at today's rates, worked out entry by entry in SQL as a snapshot would (`BillingSnapshotEntriesRepository.unbilledByClient`), and its earliest day; and next to it the time of the period in snapshots not marked invoiced, at their frozen amounts (by line, `BillingSnapshotsRepository.notInvoicedByClient`). Time on projects without a client isn't in it.

### Background jobs

`JobsService` (`src/common/jobs/`, pg-boss 10 on `DATABASE_URL`) runs the work that must happen even when Slack or the database fails for a while:
- approving and rejecting, including "Approve for Approvers" (`WorkflowDecisionsService`);
- starting a vacation workflow, asking approvers, updating their messages, finishing the request;
- telling people of the decision, the requester's DMs about where the request went and each approved level, the DM offering to log an approved time off as time (`TimeOffOfferNotifier`, when HR or an admin creates or edits a request into approved; the click is `TimeOffLogClickService`, the blocks `TimeOffOfferView`) and the one telling what logged time a change or a deletion removed, and the DM about a rejected time entry;
- the Slack events `file_shared` (CSV or Excel files: the CSV imports and the team file), `team_join`, `user_change` and `app_uninstalled` (`SlackEventsService`);
- importing the workspace's members after an install (`TeamSetupWorkflowService`), and once a day for every installed workspace (`MemberSyncScheduleService`, ten minutes after the start and then every 24 hours): Slack gives up on an event the app didn't answer, e.g. a `team_join` during a restart, and the daily import brings that person in. The import only adds the members Logbook doesn't have (`TeamUsersSyncService`), so it is safe to run again.
- asking HR which team a new person is on (`NEW_PERSON_PROMPT_JOB`, `src/team-file/constants/jobs.ts`; handler in `NewPersonPromptsService`, `src/slack/team-file`). `slack_teams.members_imported_at` is set when the first import finishes. The install and restore imports ask about nobody; a person added after the first import by a `team_join` or by the daily import (`askAboutNew` in the sync job) gets HR, or the admins, a DM with a team select and "Not yet". The job skips a person who has a team or is inactive, and a workspace with no teams, and skips recipients that already have a row in `new_person_prompts`. The first answer wins (the move applies only while the person has no team). Any placement (`USER_TEAM_CHANGED`) closes the person's open questions: `closed_at` is set by one conditional update, then the messages are updated.

Slash command replies stay in memory (`runInBackground`): a reply hours later is no use, and `trigger_id` lives 3 seconds.
- A service defines its jobs in `onModuleInit` (`jobs.define(name, handler)`) and starts one with `jobs.run(name, payload)`. Callers needn't wait; the returned promise resolves when the first run is over (it never rejects), for a caller that re-renders a tab after it.
- A decision job ends without a retry when the decision can no longer be made (the step was decided, or the user may not): those errors would only repeat.
- `run` saves the job, then runs it right away in the same process (tracked as background work). The saved copy is deleted when the run succeeds; otherwise a poller (every 30 s) retries it from 5 minutes on, up to 8 times with growing delays (about 8 hours in all). A job a stopped process never finished is retried too.
- At most `JOBS_CONCURRENCY` runs go on at once in the process, first runs and retries alike (`ConcurrencyLimit`, `src/common/utils/concurrency-limit.ts`), so that a burst of jobs leaves the pool's other connections to people's clicks; `runInBackground` work isn't limited. A job waits for its slot after it was saved, so a job must not await another job's run: with every slot held by jobs waiting for one, nothing moves (the `team_join` job starts its new-person prompt without awaiting it). A first run that gets its slot only within a minute of its saved copy's due time leaves the job to the poller, which would otherwise run it twice.
- Payloads hold IDs, and handlers load the current data: a retry may come after the request was canceled or the entry fixed, and then does nothing. A handler must be safe to run twice, because a run can fail after it did part of the work (e.g. `WorkflowStepJob.Ask` skips a step that already has a message). The exception is `WorkflowStepJob.CloseDeletedMessage`: deleting a request deletes its steps and comments (`ON DELETE CASCADE`), so `RequestWorkflowService.closeBeforeDelete` closes the steps in the transaction that deletes the request (Delete Request, and the CSV import for the user's pending requests), and each job carries its step and the comments; the message shows the request as deleted from the job's flag, as no step status says so.
- Inside `transactions.transaction()`, `await jobs.enqueue(name, payload)` saves the job on the transaction's connection and runs it after the commit; a rollback leaves no job. `jobs.enqueueMany(name, payloads, { perSecond })` saves many in one statement (pg-boss `insert`, with IDs made in the app since it returns none) and starts their first runs at most `perSecond` a second, each saved copy due 5 minutes after its own turn.
- `DATABASE_URL` is required. `JobsService` takes pg-boss from the `JOB_QUEUE` provider; unit tests pass a fake queue. pg-boss keeps its tables in the `pgboss` schema, which it creates and migrates itself; it is not exposed through the REST API.
- pg-boss 12 is ESM-only, so the project stays on 10.x (CommonJS).

### Other pieces

- **Vacation year and limits** (`VacationsUsageService`):
  - The year runs from the contract start anniversary, or over the calendar year when the user has no contract start date (`vacation-period.utils.ts`).
  - Limits come only from the vacation policy the user's team follows: its own, or the company rules' for a team that follows them and for someone in no team. With no policy, `limits` is null: usage is tracked and shown, but no balance is checked. This is the "no setup" mode.
  - Usage is counted from the requests on every read (`VacationPeriodUsageService`), not cached: a cache went stale on CSV imports and holiday or policy changes. Working days too, from the current holidays of the policy each request's team follows; a request's stored `working_days` is what it showed when it was made.
  - A request is checked against every vacation year it touches (`getVacationPeriodsBetween`), each with its days in that year, and an edited one without itself.
  - Carryover is worked out on each read (`VacationsUsageService`, from one read of the requests of every year since): in the year the person joined (`users.created_at`, `getJoinedVacationPeriod`), what HR entered on their profile (`users.carryover_days`); in each later year, what was left of the one before (its own days and its carryover), up to the policy's `carryover_days`, in calendar and working days apart. A year still to come gets none yet.
- **Working days:** `VacationDaysCalculationService` excludes weekends and the enabled holidays of the user's vacation policy. Holidays can be imported per country from Nager.Date (`src/holidays/clients/nager-date.client.ts`): only public ones (`types` holds `Public`), one per date, those of the whole country (`global`) and, when the form names one, a region's (`counties`). Choosing a country rebuilds the form with its regions after the answer (`ImportHolidaysFormActionHandler`).
- **File imports:** Slack sends `file_shared`, and `FileUploadService` routes the file:
  - `user-vacations.csv` (by name; Admin only; the `/upload-vacations` command or Users → Import vacations posts the prompt) goes to `src/user-data-import/`: sets the contract start date and replaces the user's vacations (the approvers of a pending one see their message closed), `;` separated.
  - Any other `.csv` or `.xlsx` shared in the sharer's DM with the bot (a `D…` channel; one shared in a channel is left alone, without a reply) is parsed as a team file (`src/team-file`, the Slack side in `src/slack/team-file`; Admin and HR). Its Email and Team columns tell it from other files; a file without them is told so. A CSV must be UTF-8. Teams → "📄 Set up from a file" DMs the template of everyone (`team-setup.csv`: Name, Email, Team, Team lead).
  - The file is not applied at once: the bot posts a preview (Apply / Cancel / Company rules) and keeps the upload in `team_file_uploads`, applicable for 7 days. Apply runs in one transaction under `teamFileLock` (a workspace lock, taken alone), re-plans, and applies only when the plan's digest is the one the clicked preview showed. It creates teams that follow the company rules, places people, sets leads and makes a Member lead a Manager.
  - Undo restores the workspace's latest applied upload within 7 days, and only where a value is still what Apply left.
- **Caching:** `CacheModule.register()` is in-memory, so each process has its own cache (access tokens for a day, Nager.Date holidays for an hour; cache-manager takes TTLs in milliseconds). That's fine because production runs a single instance. Running more instances would need a shared store, for example Redis via Keyv.
- **Logging:** `nestjs-pino`, pretty-printed unless `NODE_ENV=production`.
- **Health and error tracking:** `GET /health` checks the database through the pool (200 or 503); the Docker image's `HEALTHCHECK` calls it. With `SENTRY_DSN` set, `reportError` (`src/common/errors/error-reporter.ts`) sends unexpected errors to Sentry with no request data or user details: from `GlobalExceptionsFilter` (5xx), `runInBackground`, a job that won't run again, and an uninstalled workspace that could not be deleted. Every log line of a request and of the background work it starts carries the request's id (`genReqId`).
- **Errors:** a request's error is logged and answered in one place, `GlobalExceptionsFilter`. It logs once: client errors (4xx) as warnings, everything else with its stack. The answer gives a client error's own message, and only "Internal server error" otherwise. Don't log and rethrow on the way up. Errors after the answer go through `runInBackground`, which logs them.
- **Deploy:** multi-stage `Dockerfile` (Node 26 alpine, `NODE_ENV=production`, runs as the `node` user, `PORT=10000`; only `dependencies` are installed, so build and lint tools belong in `devDependencies`; `docker-compose.yml` sets `PORT` from `.env`, default 3000). The `public/` folder is served statically; the OAuth flow redirects to `/success.html`.
- **Site:** `site/` is the landing page (plain HTML and CSS, no build), published to GitHub Pages (`https://dvovna.github.io/logbook/`) by `.github/workflows/pages.yml` when `site/` changes on `main`. Its Slack fragments quote the app's real texts, so a change to those texts may need one there. `og.png`, the link preview, is rendered from `og.html` with headless Chrome (the command is in its comment). Preview it with `python3 -m http.server 4173 --directory site`.
