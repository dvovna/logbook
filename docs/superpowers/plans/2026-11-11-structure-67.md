# Structure left from the 0.2.0 review (dvovna/logbook#67)

**Goal:** move code to where it belongs, without changing what the app does. Existing unit specs move with their code; integration tests stay as they are and must pass, the round-trip guard included.

**Spec:** issue dvovna/logbook#67.

## Global constraints

- Behaviour, Slack texts and round trips stay the same. The one behaviour change is stage 5's form baseline (a bug fix).
- Repo conventions (CLAUDE.md):
  - `I`-prefixed interfaces;
  - explicit `public`/`private`;
  - imports through `@modules/…`, `@common/…` or `src/…`, never `../`;
  - domain code (`src/time-entries`, `src/time-off-logging`, `src/vacation-requests`, `src/request-workflows`, `src/common`) never imports `src/slack`;
  - types in `types/` files, values (constants) in `constants/` files, not in service files.
- Comments only for what the code can't say (why, a constraint, a race or an order). Drop comments that restate the code in every file you touch.
- Checks before each commit: `npx tsc --noEmit`, `pnpm lint`, `pnpm test`, and the integration specs that cover the moved code (`pnpm test:int <file>`; local Supabase is running).
- Commits: short imperative English one-liners, no trailers. Do not push, and do not commit `unused.json`.

## Point 5 (indexes on audit columns): closed without a change

Measured on a copy of `time_entries` (local Postgres):
- A status change is never a HOT update, with or without the `updated_by` index: `time_entries_submitted_idx` has `status` in its predicate.
- The `updated_by` index blocks HOT only when someone other than the last updater changes a non-indexed column (the minutes). On an owner's own drafts, that is rare.
- Deleting time entries by `slack_team_id` first doesn't spare the check either. Deleting a user still looks up `time_entries.created_by = <user>` across the whole table, every workspace's rows, which is the 20 s scan the index fixed.

The alternative is dropping the audit foreign keys, which trades integrity for a small write saving. Keep the indexes, and close the point in the issue with these numbers.

## Stage 1: lock order (point 4)

- `src/database/advisory-locks.ts` holds every advisory lock key, each with its rank:
  - `vacationRequestLock(requestId)` (`vacation-request:<id>`), then `workflowLock(requestId)` (`workflow:<id>`), then `timesheetLock(userId)` (`timesheet:<id>`), taken in that order;
  - the workspace locks taken alone: `clientsLock(slackTeamId)` and `billingSnapshotsLock(slackTeamId)`.
- Lock type: `IAdvisoryLock { key: string; rank: number }`.
- `TransactionService.lock(lock: IAdvisoryLock)` replaces `lock(key: string)`:
  - The transaction scope remembers the keys it holds and the highest rank.
  - Taking a lock whose rank is not above the highest held, with a key not yet held, throws before any SQL. That would be a deadlock in waiting.
  - Taking a held key again is a no-op.
- `TransactionService.lockInOrder(...locks)` sorts by rank and takes them.
- Every caller switches to these: vacation requests, time off logging (`lockInOrder`), timesheet, request workflow (`lockRequest`), clients, billing snapshots. Delete `src/time-entries/utils/timesheet-lock.ts` and `vacationTimeLock`.
- `src/database/transaction.service.spec.ts` covers:
  - in order: taken;
  - out of order: throws, and no statement is sent;
  - the same key twice: one statement;
  - `lockInOrder`: sorts the locks.

## Stage 2: time entry writes, vacation time, and who cleans up (points 1, 2)

- `TimeEntryWriter` (`src/time-entries/services/time-entry-writer.service.ts`, exported by `TimeEntriesModule`) takes from `TimeEntriesService`:
  - the row builder and `insert`;
  - `insertMany` (a row may carry `vacationRequestId`);
  - `writeUpdate`, `writeMinutes`, `writeDelete` and `writeDeletes`;
  - `deleteLinkedToVacation(requestId, slackTeamId, actorId)`, the repository's CTE behind the billed-entry guard;
  - the private `refusingBilled`, `unchangedSinceCheck` and `changedColumns`.

  Its params types go to `src/time-entries/types/`.
- `TimeEntriesService` keeps CRUD with checks: create, update, delete, submit, the finds and counts, and `announceSubmitted`. It writes through the writer. It loses `createForVacation`, `deleteVacationTime`, `insertMany`, `writeMinutes` and `writeDeletes`.
- `VacationTimeService` (`src/time-off-logging/services/vacation-time.service.ts`):
  - `log(...)`: was `createForVacation`, same parameters and errors;
  - `remove(requestId, slackTeamId, user): IRemovedVacationTime`: was `deleteVacationTime`, with the per-owner totals.

  `IRemovedVacationTime` moves to `src/time-off-logging/types/`, and `changesLoggedTime` to `src/time-off-logging/utils/`.
- `VacationRequestsService` no longer knows time entries: no `TimeEntriesService`, and no `TimeEntriesModule` in `VacationRequestsModule`.
  - `checkUpdate(findParams, changes, user): IVacationRequestUpdate`: everything before today's transaction, with the same parallel reads.
  - `applyUpdate(update, user): { previous, request }`: in the caller's transaction, under `vacationRequestLock`. It re-reads the request, writes, and emits nothing.
  - `update(...)` is `checkUpdate`, then a transaction with the lock and `applyUpdate`, then emits `Updated(request, user, previous)`. It is used by `cancel` and needs no cleanup: a pending request holds no logged time, because logging needs an approved request and leaving approved removes it.
  - `applyDelete(request, user)` closes the approvals and deletes the request, in the caller's transaction. `delete` goes away.
- `TimeOffChangesService` (`src/time-off-logging/services/time-off-changes.service.ts`):
  - `update(findParams, changes, user)` and `delete(findParams, user)`, each returning `IVacationRequestChange { request, billedDates }` (the type moves here). Each runs one transaction under `vacationRequestLock`: the request's change, then `VacationTimeService.remove` (for a delete, before the request goes).
  - After the transaction it emits `Updated` or `Deleted` with `TimeOffChangedEvent` (`src/time-off-logging/events/`), which extends `VacationRequestUpdatedEvent` with `removedTime?`. `VacationRequestUpdatedEvent` loses `removedTime` and its time-entries import.
- Slack:
  - the admin request form and Delete Request call `TimeOffChangesService`;
  - the offer service types its events as `TimeOffChangedEvent`;
  - `TimeOffLoggingService.log` uses `lockInOrder` and `VacationTimeService.log`;
  - the timesheet writes through `TimeEntryWriter`.
- Specs move with the code (`vacation-time.service.spec.ts`, `time-off-changes.service.spec.ts`).

## Stage 3: timesheet read and save, the form out of the domain (points 1, 3)

- `TimesheetService` becomes two services:
  - `TimesheetWeekService`: `getWeek`, `getForm`, `findOpenBefore`, `allowedProjects`, and, for the save, `loadProjects` and `findEntries`;
  - `TimesheetSaveService`: `saveCells`, with the cell checks and the writes through `TimeEntryWriter`.
- Pure helpers (`buildCell`, `byClientAndName`, `isNotCancelled`) go to `src/time-entries/utils/timesheet-cells.ts`, and the internal types to `timesheet.types.ts`.
- Domain cells:
  - `ITimesheetCellInput` becomes `ITimesheetCellChange { projectId; date; minutes; expectedMinutes }`. A cell that no longer holds `expectedMinutes` is refused.
  - Errors about a cell are a `TimesheetCellError` (`src/time-entries/errors/`), a `ValidationError` carrying `cell: { projectId, date }` and, for a locked cell, its `lock`.
- The domain names no `block_id` and words no lock:
  - `cellKey` moves to `src/slack/tabs/time-tracking/utils/`.
  - The lock wording (today's `LOCK_MESSAGES`) goes into one Slack dictionary, which both the form view and the submit handler use. The submit handler turns a `TimesheetCellError` into an error at `cellKey(cell)`, with the lock's words.

## Stage 4: the time off offer and the action errors (points 1, 6)

- `TimeOffOfferService` splits into:
  - `TimeOffOfferNotifier`: the events, the job and the DMs;
  - `TimeOffLogClickService`: the click, refusing it, the ephemeral messages and the result;
  - `TimeOffOfferView`: an injectable view with the button (used by the decision DM), the offer section, the removal text and the result section.

  Its constants and types go to `constants/` and `types/`.
- One classifier of errors for Slack actions and forms, `src/slack/common/utils/action-errors.ts`:
  - **refusal** (told to the user): `ValidationError`, `NotFoundException`, `DuplicatedRecordError`, `MaxItemsCountReachedError`, `EntityHasDependenciesError`, `PrimaryEntityDeleteError`;
  - **forbidden**: `ForbiddenException`;
  - **unexpected**: anything else.

  It is used by the click service, the Approvals and My time action handlers, and `BaseModalFormSubmitHandler`. Each keeps how it shows them: a modal shows a forbidden message, while a message button drops it with a warning.

## Stage 5: forms (point 6)

- **Form parser interface.** `IFormParser<T> { parse(view); blockIdOf(field, view) }` is what `BaseModalFormSubmitHandler` takes:
  - `BaseValuesParser` implements it;
  - the timesheet parser answers for cells;
  - the `blockIdOfField` hook goes away, while `errorFields` stays in the handler.
- **The week form keeps its first baseline across rebuilds** (Add a project, Show weekend, day, an error):
  - A rebuild takes the shown minutes of the cells it already showed from the current view (`initial_value`), and only new cells read the database.
  - New integration test: a cell changed elsewhere between opening and a rebuild, then typed into, is refused at that cell.
- **The report form's quick period passes `view.hash` to `updateView`.**

## Stage 6: validation and a deleted workflow step (point 6)

- **`TimeEntriesValidationService` keeps one path per rule.** The `validate*` methods read what a rule needs (billed, the day's minutes), then call the `check*` ones.
- **`WorkflowStepStatus.Deleted` goes away.** The job that closes a deleted request's messages, and the approver message view, render a deleted request from an explicit flag, not from a status that is never stored.
